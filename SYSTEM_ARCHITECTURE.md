# System Architecture — Sales Executive Management Platform

> Multi-tenant, modular, and reusable architecture built with Flutter (MVVM + Clean Architecture) and FastAPI. Designed for strict environment isolation, industry-standard modularization, and a three-layer deployment model to support client-hosted databases and in-house SMS.

---

## 1. High-Level Goals

- **Reusability & Modularity**: Feature-based modules, clean boundaries (presentation/domain/data), and package-level reuse.
- **Multi-Tenant**: Serve multiple client organizations securely from a single deployment (logical tenant isolation).
- **Three-Layer Architecture**: 
  1. **Client Apps (Flutter)**
  2. **Public API Layer (FastAPI: API Gateway/Auth/Feature APIs)**
  3. **Private Data Layer (Middleware Service + DB inside client/company network)**
- **Operational Excellence**: CI/CD, environment separation, observability, auditability, and principle-of-least-privilege RBAC.
- **Ethical Access**: No "secret backdoors." Use a **break-glass** emergency access model with full auditing (see §11).

---

## 2. Core Roles & Tenancy

- **SUPERADMIN (Platform Owner)** — manages all client tenants, contracts, plans, feature flags, global monitoring.
- **CLIENT-ADMIN** — manages Area Managers & Sales Executives; approves profile/shop changes; views org-wide analytics.
- **AREA MANAGER** — manages territories, routes, approvals for weekly plans; sees team/territory analytics.
- **SALES EXECUTIVE** — visits shops, check-in/checkout with geolocation, remarks; sees personal performance analytics.

**Multi-Tenant Model**
- `tenant_id` required on every business entity.
- Configurable branding, territory hierarchies, and feature toggles per tenant.
- Data access always filtered by `tenant_id`.

---

## 3. Deployment Topology (Three Layers)

```
[Flutter Apps]
| HTTPS (JWT)
v
[Public API Layer - FastAPI API Gateway]

Auth, RBAC, Rate limiting, Validation

Feature APIs (routes, visits, shops, analytics)

Sync API (pulls from client "Tally-like" system via Data Layer)
| gRPC/HTTPS (mutual TLS) + message queue (optional)
v
[Private Data Layer - Middleware Service]

Runs inside company/client VPC/VNet with DB

Executes queries via SQLModel/SQLAlchemy (MySQL)

ETL/Sync workers & schedulers

Caches/materialized views build
v
[MySQL DB (Production) — private network only]
```

- **Public API Layer** never talks directly to the private DB in production.
- **Private Data Layer (Middleware)** is the only process that reaches the DB. It exposes a narrow, vetted contract to the Public API Layer.
- Optional **MQ** (e.g., RabbitMQ/SQS) for ETL jobs and heavy analytics builds.

---

## 4. Network & Security

- **VPC Segmentation**: API Gateway in public subnet; Data Layer + DB in private subnets.
- **mTLS** between API Gateway and Data Layer. Service accounts & short-lived credentials.
- **JWT** for end-user auth; **role + tenant** claims.
- **Row-Level Security (enforced in services)** via consistent `tenant_id` filtering.
- **Audit Trails**: Every admin action and approval is logged (immutable log store).
- **Secrets**: Stored in cloud secret manager; 12-factor config.

---

## 5. Authentication & OTP

- **In-house SMS** (hosted on AWS): production OTP sent via internal SMS service.
- **Development Mode**: OTP generated by backend and **printed to server console logs** to simplify testing.
- **Phone number is the primary identifier**; JWT issued post-OTP verification.

## 6. Feature Overview & Data Flow

### 6.1 Territory & Routing
- Client-admin defines **territories** → assigned to **Area Managers**.
- Area Managers plan weekly routes for Sales Executives.
- Route suggestion engine (rule-based first; ML-ready) considers:
  - Outstanding dues (>30 days),
  - Time since last visit,
  - Order renewal windows,
  - Executive capacity & travel constraints.

### 6.2 Shop Visits & Tracking
- Sales Executive **Check-in** requires GPS location & timestamp.
- **Check-out** captures duration, remarks, next steps.
- Optional photo upload or attachment (receipts/shelf photos).
- Offline-first queues on device; synced reliably.

### 6.3 Finance & Orders (Read-Only for Analytics)
- Client provides **Tally-like API**. We ingest daily:
  - Orders, line items, statuses,
  - Payments, outstanding balances,
  - Product master data (SKU, category).
- **Middleware ETL** normalizes and writes to analytics tables.
- No write-backs to client finance system.

### 6.4 Approvals & Workflows
- **Profile updates** (Sales Executive / Area Manager), **Shop additions/edits** require Client-Admin approval.
- Workflow states: `PENDING -> APPROVED/REJECTED` with audit entries.

### 6.5 Analytics
- Per-role dashboards:
  - **Sales Executive**: visited shops, visits per day/week, monthly sales (read-only), top products/shops.
  - **Area Manager**: team performance, best territories/shops, overdue balances, route efficacy.
  - **Client-Admin**: org-wide rollups; drill-downs to any team/user.
  - **Superadmin**: cross-tenant usage, error rates, cost dashboards.
- Materialized views refreshed by schedulers; hot-path metrics cached.

## 7. Service Modularization

- **API Gateway (FastAPI)**  
  - Modules: `auth`, `users`, `tenants`, `territories`, `routes`, `shops`, `visits`, `analytics`, `approvals`, `files`, `sync`.
  - Pure HTTP interface for clients; calls Data Layer via mTLS.

- **Data Layer (Middleware Service)**
  - Modules: `dal` (repositories), `etl_sync` (client API ingestion), `analytics_builder`, `approvals_engine`.
  - Strict contracts exposed to API Gateway; enforces tenant scoping.

- **Workers & Schedulers**
  - Daily sync with client finance API.
  - Periodic recalculation of materialized views.
  - Dead-letter queues and retries for resilience.

## 11. Admin Access Policy (Important)

*We will not implement a hidden "secret login" (backdoor). It's unsafe, unethical, and may be illegal.*

**Safer alternative — Break-Glass Access:**

- A dedicated break-glass superadmin role disabled by default.
- Activation requires multi-party approval (e.g., 2 approvers), time-bound tokens, and reason code.
- All actions fully audited and auto-notified to relevant stakeholders.
- Post-incident review is mandatory.
